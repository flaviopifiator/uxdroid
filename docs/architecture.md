# uxdroid architecture

uxdroid runs Android APKs as ordinary Linux processes: no container, no VM, no Android system image. It turns an APK into a host executable backed by a shared runtime, and implements the Android platform as libraries on top of Linux.

## The four layers

| Layer | Responsibility | Language |
|-------|----------------|----------|
| APK tooling | Parse the APK, plan execution, compile DEX ahead of time, generate the launcher | Rust |
| Native bridge | Load bionic-linked `.so` files under glibc, translate foreign ABIs | Rust |
| Managed runtime | Execute DEX as machine code | ART (C++, reused) |
| Platform | `android.*` API: AOSP's framework, with the natives and system services below it implemented over Wayland, Vulkan/EGL and PipeWire | Java/Kotlin + Rust |

## What "native executable" means

An APK holds two kinds of code, and they take different paths:

| Code | Path | CPU translation |
|------|------|-----------------|
| DEX bytecode | `dex2oat` compiles it to x86_64 at install time | None |
| `.so` for the host ABI | Loaded directly by the bridge | None |
| `.so` for another ABI (usually `arm64-v8a`) | Runs through a binary translator | Yes, this is the only emulated path |

The result is a launcher ELF plus compiled artifacts. It still needs the shared runtime and platform libraries, the same way a Java or Python program needs its runtime.

## Decisions

### Rust for everything we write natively

Go is rejected for this layer. ART installs signal handlers and relies on `SIGSEGV` for implicit null checks, and the bridge must control TLS, stacks and the calling convention. Go's runtime owns signals and goroutine stacks, adds cgo cost on every JNI crossing, and adds a garbage collector next to ART's. Rust has no runtime to conflict with and calls C at zero cost.

### Reuse ART, do not rewrite it

A competitive DEX runtime means a compiler, a garbage collector and years of tuning. ART is Apache-2.0 and already does this. Performance work goes where Android-on-Linux loses time: startup, IPC and graphics paths.

### No Binder in the app process path

Inside one app, a platform service call becomes a direct in-process call instead of an IPC round trip. This is the main performance advantage over a container and removes the kernel module requirement. Cross-app features need a separate design when we reach them.

### Reference code stays reference

Android Translation Layer (ATL) is GPL-3.0-or-later. We study its approach but copy no code from it, so uxdroid's license stays an open choice. AOSP code is Apache-2.0 and can be reused with attribution.

### The loader binds to glibc only what was audited

bionic and glibc share most symbol names but not their ABI. Probes compiled against both measured `sigset_t` at 8 and 128 bytes, `jmp_buf` at 88 and 200, `regex_t` at 32 and 64, different `sysconf`, `pathconf` and `EAI_*` constants, and `addrinfo` with two fields swapped. Passing those calls to glibc corrupts memory with no error, and a list of known bad symbols can never be complete. So the default is to refuse:

| Symbol | Result |
|--------|--------|
| Exported by an Android system library the library needs, such as `libandroid.so` | Binds to that library's signature table, below |
| Listed in `crates/bridge/src/glibc_compatible.txt` | Binds directly, with no added cost |
| Different ABI, translatable | Binds to a shim in `crates/bridge/src/shims.rs` |
| A function in glibc that nobody audited | Loads, and stops the program naming the symbol if it is called |
| Data in glibc that nobody audited | The load fails, because data cannot trap |
| Found nowhere | The load fails, listing every missing name |

Printing a `long double` also stops by name, because the `printf` family checks its format. To support a new symbol, compare its signature, structs and constants against the NDK headers, then add it to the list. The audit covers signatures, measured layouts and constants, and individual behavior differences can remain, such as `sysconf` returning `EINVAL` for names not yet mapped.

One way around this rule remains: ART calls glibc's `dlopen` first, so a library with no `DT_NEEDED` entries loads through glibc and binds without the audit. Checking the bridge first needs a small patch to `libnativeloader`.

App code names files of Android's system partition by absolute path, such as Skia reading `/system/etc/fonts.xml`. The functions that take a path, such as `open`, `fopen`, `stat` and `opendir`, are shims that move `/system` to the runtime root `ANDROID_ROOT` names, as the framework's rewritten paths do; every other path reaches glibc unchanged. A segment whose file cannot be mapped executable, because its mount is `noexec` like the sandbox's `/tmp`, is read into anonymous memory instead, which costs its sharing between processes.

Not translated yet: static initializers with non-zero bionic values, such as `PTHREAD_RECURSIVE_MUTEX_INITIALIZER`. Libraries using ELF TLS, which means a minimum SDK of 29 or higher with `thread_local`, are rejected.

### ART is built for the host, not borrowed from a device

ART's host build links against a glibc 2.17 sysroot and needs no bionic, so `dalvikvm` is an ordinary Linux program. A device APEX was rejected: it writes bionic's TLS slots, which overlap glibc's thread control block. The pinned `master-art` tree downloads with `runtime/art/sync.sh` and builds in Docker with `runtime/art/build.sh`, and the result runs in a plain Ubuntu with no Android tree.

### One process, joined through NativeBridge

`uxdroid run` replaces itself with `dalvikvm`. ART tries glibc's `dlopen` on an app's native library, which fails for anything linked to bionic's `libc.so`, then falls back to `crates/nativebridge`, a Rust library that loads it with the bridge. CPU and calling convention match, so a JNI call goes straight to the function's address with no translation. This same hook is where `arm64-v8a` translation will attach. `crates/platform` holds the native half of the `android.*` classes in `platform/java`. The classes are on the class path for now, and will move to the boot class path when there are enough to be worth compiling into the image.

The window, audio and GPU stay behind this layer, so a later macOS port does not reach into the rest.

### Android's system libraries are signature tables

App libraries name `liblog.so`, `libandroid.so`, `libjnigraphics.so`, `libEGL.so`, `libGLESv2.so`, `libGLESv3.so`, `libOpenSLES.so`, `libaaudio.so` and `libmediandk.so` in `DT_NEEDED`, or open them with `dlopen`, as oboe opens `libaaudio.so`. None of them is a file. Each is a table of `uxdroid_bridge::table`: every export with its host address and its signature in a closed vocabulary, such as `i32(i32,ptr,ptr,...)` for `__android_log_print` or `ptr` for an object like `SL_IID_ENGINE`. `liblog`'s table is in the bridge, next to the printf machinery it shares with bionic's libc, and every library sees it, as on Android, where `app_process` links it. The others are in `crates/ndk`, and `crates/nativebridge` hands them to the loader before the first app library loads. A library searches its loaded dependencies first, then the tables it needs, then the shims, and a name its table lacks is reported missing like any other. The EGL and GLES tables are generated from the NDK's headers and stubs by `crates/ndk/generate.sh`.

| Library | Served by |
|---------|-----------|
| `liblog` | The stderr the process started with, with the minimum priority, default tag, logger and aborter an app may set |
| `libandroid` assets | The framework's `AssetManager`: each asset is read into memory when it opens, and stored entries also open as file descriptors |
| `libandroid` looper | One epoll set per thread. On a thread with a Java `Looper`, `MessageQueue.addOnFileDescriptorEventListener` watches that set, so the app's callbacks run inside `Looper.loop` |
| `libandroid` choreographer | `AChoreographer`: one per thread with an `ALooper`, a timer on that looper armed by the same frame clock as the framework's `Choreographer`, which `libuxdroid_system.so` hands over by address through `VsyncListener.clock()` (a 60 Hz clock of its own without it). Frame callbacks, 32- and 64-bit and delayed, vsync callbacks with one frame timeline, and refresh rate callbacks, which hear 60 Hz once. Flutter's engine finds it and paces its frames by it |
| `libandroid` native window | The Java `Surface`: a lock hands out a buffer, and posting copies it into a `Bitmap` and draws it through `Surface.lockCanvas` |
| `libjnigraphics` | `Bitmap.getPixels` and `setPixels`, converted to Android's memory layout |
| `libEGL` | The GPU through EGL's GBM platform on the first render node whose display imports dmabufs and has pbuffers, else Mesa's surfaceless platform, with llvmpipe when there is no GPU. A window surface is a pbuffer; on the GPU each swap blits it into a dmabuf the compositor shows, otherwise it reads it back into its native window. Configs report `EGL_WINDOW_BIT` and Android's visual IDs |
| `libGLESv2`, `libGLESv3` | Mesa's own functions, at no added cost |
| `libOpenSLES` | An engine, output mixes, PCM buffer-queue audio players and recorders over `crates/audio` streams. Interface pointers are resolved back to their object and checked as live. Players of URIs and file descriptors, which need a decoder, are refused. The interface IDs are data, bound on purpose: each is a pointer to a GUID of ours, and apps compare the pointers |
| `libaaudio` | AAudio streams over `crates/audio`: data callbacks on the stream's thread, adapted to the size the app asks for, and blocking reads and writes with timeouts |
| `libmediandk` | `AMediaFormat` as a typed key/value store in insertion order, as AOSP's `AMessage`, with its `AMEDIAFORMAT_KEY_*` strings as data; a string or buffer handed out lives until its key is set again or the format ends. No codec is offered yet: every `AMediaCodec` lookup returns null, as Android does for a type it has no codec for, so apps take their software path, and every call on a codec handle returns `AMEDIA_ERROR_INVALID_OBJECT`. Extractors refuse every source as unsupported, and no crypto or DRM scheme exists. Hardware codecs come with streaming, through Vulkan Video |

The log is not the app's descriptor 2, as Android's is a daemon: an app may point its stdout and stderr at a pipe and copy what it reads into the log, as AnkiDroid's Rust backend does, which looped every line back into the pipe, uxdroid's own messages included. Each of uxdroid's libraries keeps a duplicate of descriptor 2 as it loads, before any app code runs (`uxdroid_bridge::output`), and `liblog`, `android.util.Log` and uxdroid's messages write there; `Boot` points `System.out` and `System.err` at duplicates of their own descriptors too, as Android sends them to the log rather than to the app's descriptors.

GPU rendering uses only vendor-neutral interfaces: EGL through glvnd on the GBM platform, dmabufs handed to the compositor through `zwp_linux_dmabuf_v1`, and later Vulkan Video for encoding, so the product loads whatever driver the host has and adds no vendor dependency. For development, the `dev-gpu` service (compose profile `gpu`) passes the host's GPU nodes into `dev` and mounts the host driver's user-space libraries read-only, the set a CDI spec would inject, with no vendor package installed; `runtime/gpu/gpu_probe.sh` reports which renderer a headless GLES 2 context gets, llvmpipe in `dev` and the host GPU in `dev-gpu`, and, through `dmabuf_probe.c`, every display's EGL extensions and whether the dmabuf path below works. The `sandbox` service stays on llvmpipe.

An app's EGL frames reach the compositor without copies this way (`crates/ndk/src/gpu.rs`):

1. The display. GBM opens the first render node, `/dev/dri/renderD128` up, and EGL's GBM platform makes a display on its device, kept only when it has `EGL_EXT_image_dma_buf_import` and pbuffer configs; otherwise Mesa's surfaceless display, as before. `UXDROID_EGL=readback` keeps the surfaceless display, which glvnd may still put on the GPU's vendor library, with frames read back.
2. The window surface stays a pbuffer, the app's framebuffer 0, on every path. On the GPU a swap blits it, upside down since GL's rows go up and a dmabuf's go down, into the next free buffer of a swapchain of two, growing to three while the compositor holds the others: GBM buffer objects allocated with the modifiers the compositor lists for ARGB8888, each imported as an `EGLImage` behind a renderbuffer of its own framebuffer. The swap saves and puts back the framebuffer bindings, the scissor test and rasterizer discard it touches. A GBM window surface would save the blit, but NVIDIA's driver refuses one on a render node (`EGL_BAD_ALLOC`), so the blit is the path every driver takes.
3. Before the compositor reads, the swap waits for the GPU on an `EGL_KHR_fence_sync` fence (`glFinish` without one), since NVIDIA's dmabufs carry no implicit fences; `EGL_ANDROID_native_fence_sync` is there on NVIDIA but would need the compositor's explicit synchronization (`linux-drm-syncobj-v1`), which is not used yet.
4. The dmabuf goes to `libuxdroid_system.so` through `uxdroid_ndk::present::Presenter`, whose address that library hands over beside its frame clock (`VsyncListener.clock()`, version 2), with the `Surface`'s `mNativeObject` naming the layer. A window's own layer with no children shows it as its frame; a child layer, such as a `SurfaceView`'s, shows it on a plane, below.
5. Each buffer gets its `wl_buffer` once, through `zwp_linux_buffer_params_v1.create`, whose `failed` event is a refusal the app survives, unlike `create_immed`'s; a buffer is busy from its attach until `wl_buffer.release`, and a swap that finds all three busy for 50 ms reads that frame back.

Frames are read back as before when there is no render node, GBM, extension, OpenGL ES 3 context (for `glBlitFramebuffer`) or compositor that imports dmabufs, when framebuffer 0 is multisampled, before the window has opened, and while the layer is not shown as it is: scaled, turned, translucent, rounded or clipped. Each of these is said once, as `uxdroid: EGL frames are read back: <why>`. Weston's pixman renderer, the tests' default compositor, imports no dmabufs; its GL renderer does, on the GPU (`runtime/gpu/compositor.sh`, `RENDERER=gl`), and `runtime/gpu/gpu_smoke.sh` checks the whole path there. NVIDIA's driver, probed in `dev-gpu`, has every extension used, and also `EGL_MESA_image_dma_buf_export`, which Mesa's llvmpipe lacks; nothing uses that export, so the path stays the same on every driver.

Pixels cross into Java as `int` arrays, because AOSP's host graphics library cannot take NIO buffers on ART: it looks up OpenJDK's `FileDescriptor.fd`. A native window frame is therefore copied three times before it reaches Wayland, and an EGL frame read back once more. EGL frames on the GPU path above are not copied at all; a buffer shared with the Wayland window would remove the copies of software frames too.

A translator needs more than the tables: callbacks into app code, such as `ALooper` callbacks and an app's logger, and host functions handed out as pointers, such as `eglGetProcAddress` results and OpenSL ES method tables, cross the same boundary. OpenSL ES's method tables and the audio callbacks, OpenSL ES buffer queues' and AAudio's, already have signatures, in `uxdroid_ndk::opensles_interfaces`.

The framework's Java GL bindings go to the same EGL and GLES: `android.opengl.GLES20` to `GLES32`, and the EGL10 of `javax.microedition.khronos` that `GLSurfaceView` uses (`com.google.android.gles_jni.EGLImpl`), are JNI code of `libandroid_runtime` on Android, which AOSP's host build leaves out, so they had default bodies and Mindustry stopped with "Arc requires OpenGL ES 2.0". Now `crates/system/src/gl` registers them at startup on their classes, loaded but not initialized. The GLES natives are generated (`gles.rs`, by `gles_jni.py`, run through `runtime/framework/gles_jni.sh`) from the framework's own declarations, and each call is checked against the NDK headers' signature table for its number of C arguments, so a Java form whose arguments differ from C's, such as a name buffer that carries its own size, must be written by hand. An array passes from its offset and a buffer from its position, a direct buffer's memory or a heap buffer's array pinned only around the call, and each must hold what GL writes or reads, by rules from the function's count, the state name of a `glGet`, or the rectangle of `glReadPixels`; a short one throws `IllegalArgumentException`, as AOSP's bindings do. Client vertex arrays need a direct buffer, as there. `GLImpl`, the GL10 a renderer is handed, answers the functions it shares with GLES, such as `glGetString`; its fixed-function rest and `EGL14` keep their default bodies. A few GLES natives whose Java form drops an argument C takes, such as `glObjectPtrLabel`, `glGetPointerv` and `glGetDebugMessageLog`, or that pass arrays of strings, such as `glCreateShaderProgramv`, throw `UnsupportedOperationException` with their name. The border color of the texture and sampler parameter calls holds four values, and so does `GL_COLOR_WRITEMASK` read by draw buffer through `glGetBooleani_v`, so a shorter array is refused there too; client indices of `glDrawElements` and its range, instanced and base-vertex forms must hold their count of their type, and a null or short buffer is refused, as AOSP's bindings refuse it. A window surface from `eglCreateWindowSurface` on a SurfaceView is the same pbuffer read back into the `Surface` at each swap; `libuxdroid_system.so` holds its own copy of that state, so a surface is swapped through the API that made it.

Not yet: `ASurfaceControl` and `ASurfaceTransaction` (Flutter's Impeller would use them with `AHardwareBuffer`, which does not exist here), `AHardwareBuffer` and Android image extensions for EGL, OpenSL ES players of encoded data and its event callbacks, and the rest of `libandroid`, such as sensors, input queues and configuration.

### The platform is AOSP's own framework

Writing the `android.*` API ourselves would never end. A spike ran AOSP's real Android 16 framework on our host ART instead: a framework `TextView` measured itself and drew text through the real Skia and Minikin, reading the real `framework-res.apk`. What the framework expects from below is much narrower than its public API:

| Below the framework | Who provides it |
|---------------------|-----------------|
| Graphics, text, resources, input events, `MessageQueue` | AOSP's host `libandroid_runtime`, built for glibc |
| Natives nobody implemented yet | A default body that returns the type's zero, bound at install time and logged when called |
| Logging, properties, clocks, local `Binder` objects, `Parcel` | Our natives |
| `SurfaceControl`, `BLASTBufferQueue`, `Surface`, `DisplayEventReceiver` | Our natives, over Wayland and a timer |
| `InputChannel`, `InputEventReceiver`, `KeyCharacterMap` | Our natives, over the Wayland seat and its keymap |
| System services | In-process proxies of their AIDL interfaces, with no IPC; unimplemented calls return defaults and are counted |

`crates/system` holds our natives and the default bodies: install time lists every framework native in `framework/natives.txt`, and each gets a 32-byte stub that reports its first call and returns zero. `uxdroid install` writes those stubs once, into a library beside the app, `defaults.so`, whose functions carry the names JNI looks natives up by (`Java_<class>_<method>`, with the arguments for overloads); a start only loads it, and ART binds a stub the first time a native nobody registered is called, so the classes of the other natives are not loaded at startup and the stubs are clean file pages. Without that library, or when its file system cannot map it executable, every listed native gets its stub at startup, as before; that costs about 11 ms. `dev.uxdroid.system.Boot` runs the startup order. `dev.uxdroid.system.Services` serves each system service as a proxy of its AIDL interface and reports the first call of every method nobody handles, and `AppContext` extends a `DefaultContext` generated from `android.content.Context` at install time. A default body that matches the native-object pattern returns more than zero: in a class whose native hands `NativeAllocationRegistry` a free function, the natives that create objects return a fresh small allocation and that function frees it, because the registry refuses null. Libraries the framework loads by name only for natives that already have default bodies, such as `libstats_jni.so`, are installed empty.

`android.os.Parcel` is ours too, in `crates/system/src/parcel`: AOSP's host library carries Parcel's method table but no entry that registers it, so before this every parcel had a null native pointer and read back zeros. A parcel is a growable buffer in Android's wire format, after AOSP's `Parcel.cpp`: values little-endian at 4-byte alignment, `String16` and `String8` as a length, the characters, a terminator and zero padding, byte arrays and blobs length-prefixed, blobs always in place, and the interface token with Android 16's strict-mode policy, work source and `SYST` header in front of the descriptor. Buffers grow by half of what they need, from 128 bytes. Binders and file descriptors are 24-byte `flat_binder_object` records whose objects stay in a table beside the bytes: a binder is a global reference to the Java object itself, so a binder read back is the same object, and a file descriptor is the parcel's own duplicate, duplicated again for each read. A binder or file descriptor is found only at an offset where this process wrote one, so bytes from outside, such as an unmarshalled array, never hold one, and a parcel holding objects refuses `marshall`, as on Android. Every length and offset read from a parcel is checked against its data, and reading plain data over an object fails as `validateReadData` makes it, so foreign bytes never reach memory past the end and never make a parcel allocate more than they hold. `mNativePtr` is the address of the Rust parcel, as Android's is of its C++ one, because `writeInt` and its kind are the framework's hottest natives. `runtime/framework/parcel_smoke.sh` passes a Bundle with nested Parcelables, an Intent with extras, a `ParcelFileDescriptor` over a pipe, a binder and a call through the framework's generated `IResultReceiver` proxy and stub, and checks that no Parcel native has a default body. In the sample app and RustDesk, the framework's only parcel is the metadata one each `SurfaceControl` passes to its native, which is now a real, empty parcel.

The host library's own natives that take a parcel cannot read ours: it reaches a parcel through field ids that only its unregistered Parcel table sets, so writing a `Bitmap` into any parcel used to abort the process with `fid == null`. Bitmap's pair is replaced by `dev.uxdroid.system.BitmapParcels`, which copies the pixels through Bitmap's other natives into a blob of unpremultiplied ARGB words after a header, and checks the header's size against the blob before allocating; semi-transparent pixels of a premultiplied bitmap can change by rounding, while an unpremultiplied one's come back exactly, and a hardware bitmap comes back in memory. `MotionEvent`, `KeyCharacterMap`, `Region`, `Gainmap` and `CursorWindow` need the library's C++ objects, so their parcel natives throw `UnsupportedOperationException` with the method's name. Measured from disk against the previous library in the same session (`benches/framework/measure.py`, 20 runs for `FrameworkSmoke` and the sample app, 10 for RustDesk), startup and memory did not change: peak RSS, PSS and private dirty memory stayed within 0.2 MiB for the framework rows and 1.3 MiB for RustDesk, and warm times within the noise of a shared machine (sample app 292 and 274 ms, RustDesk 588 and 461 ms, old and new).

`dev.uxdroid.system.Launcher` starts an app the way Android does, after `uxdroid install` has done the installer's part: the APK's native libraries for the chosen ABI are extracted into `ANDROID_DATA/data/<package>/lib`, where `ApplicationInfo.nativeLibraryDir` points, and the ABI is recorded beside them. With the framework at hand, the install also fills the code directory `ANDROID_DATA/app/<package>`, as Android's does: the APK as `base.apk`; its DEX compiled by `dex2oat` against the boot image with the class loader context the launcher gives the app, `PCL[]` under the framework's `PCL`, using the `verify` filter, which measured fastest to RustDesk's first frame and lowest in memory (`speed-profile` has no profile to use, since this ART cannot read the version-010 baseline profiles APKs ship); `package.record`, the framework's own parse of the manifest, written field by field by `dev.uxdroid.system.Installer`; and `defaults.so`, below. The launcher reads the record, valid only for the runtime files and the `base.apk` it was made with, or parses the APK with the framework's `PackageParser` when there is none or it is stale, and calls `ActivityThread.main`, which attaches to `IActivityManager`. That service is a handler in the same process: it calls `bindApplication` and schedules a `ClientTransaction` with a `LaunchActivityItem`, so the framework itself makes the `LoadedApk`, the `Application`, the `Activity` through `Instrumentation`, its `ContextImpl` and its `PhoneWindow`. The launcher plays `system_server` for what an app receives at bind: the memory of `ApplicationSharedMemory` (natives in `crates/system`), one display, one unlocked user, the app's own content providers, and system content providers such as Settings as `IContentProvider` proxies. One difference from Android remains: the framework is on the system class path, not the boot class path, so the launcher caches the app's `LoadedApk` with the system class loader as parent before the bind runs. A `LoadedApk` looks the manifest's `appComponentFactory`, such as androidx.core's `CoreComponentFactory`, up on that base loader as it is made, which on Android is null and skips it, so the launcher hides the factory until the app's own loader looks it up.

Without `--once`, the launch transaction also holds a `ResumeActivityItem`, as `ActivityTaskManager` sends for an Activity in front, so `handleResumeActivity` adds the decor view through `WindowManagerGlobal` and the framework's `ViewRootImpl`. `WindowService` answers `IWindowManager.openSession` with an in-process `IWindowSession`: `addToDisplayAsUser` reports a window with no system bars, and `relayout` gives each window a layer the size of the display (400x700 dp at 160 dpi) through `SurfaceControl.Builder`. Below it, `crates/system` implements the natives that `system_server` and SurfaceFlinger back on Android:

- `SurfaceControl` and `BLASTBufferQueue` only name a layer and its size. Handles are ids in a registry, never addresses, so the free functions `NativeAllocationRegistry` runs on its own thread cannot touch freed memory.
- `Surface.lockCanvas` points the framework's own `Canvas` at a `Bitmap` the size of the window, and `unlockCanvasAndPost` copies its pixels into the shared-memory buffer of the window's Wayland surface, opened on the first lock: milestone 3's window, rewritten in `crates/system` with a seat and reading without blocking.
- The process has one Wayland connection, and its one toplevel is the display: the first window is the toplevel's surface, and later windows, dialogs, popups and menus, are subsurfaces of it at the frame the window manager computed, as Android's `DisplayPolicy` does from the window's size, gravity, x and y, moved back by its surface insets, the room a dialog keeps for its shadow. Subsurfaces were chosen over `xdg_popup`: Android places every window itself in display coordinates and dismisses popups itself, through `ACTION_OUTSIDE` and touch-modal windows, while an `xdg_popup` is placed by the compositor's positioner, needs a grab from a recent input event, and is dismissed by the compositor; and a dialog is no popup. Each subsurface is desynchronized, so a window's frame shows when it posts, and the compositor composes them, so a dialog's frames never redraw the activity's. `crates/system/src/windows.rs` routes input as InputDispatcher does: a pointer or touch goes to the top window under it, or to a touch-modal window above it (focusable, without `FLAG_NOT_TOUCH_MODAL`), which is how a dialog sees touches outside it and cancels; a window with `FLAG_WATCH_OUTSIDE_TOUCH` above the touched one gets `ACTION_OUTSIDE`; a gesture stays with the window it started in; and keys and focus go to the top focusable window, so a dialog takes the keyboard and gives it back when it goes. A removed window's surface leaves the display at once.
- A configure of the toplevel with a new size resizes the display: `WindowService` calls each window's `IWindow.resized` with the frames and configuration of the new size, the framework lays its views out again, and the next lock gives the window a buffer of that size. A close of the toplevel closes the task: each activity is paused, stopped and destroyed as finishing through `DestroyActivityItem`, then the process exits. `runtime/framework/compose_smoke.sh` checks all of this and the composition above through the scripted compositor. Drawing is software: the launcher clears `ThreadedRenderer.sRendererEnabled`, the framework's own switch for devices without GPU rendering, so `ViewRootImpl.drawSoftware` runs. `Bitmap.getPixels` yields 0xAARRGGBB, which is Wayland's XRGB8888 whatever Skia's byte order. A window whose layer is translucent, by its `PixelFormat` (a dialog's is `TRANSLUCENT`, for its shadow) or `Transaction.setOpaque`, gets an ARGB8888 buffer instead, composed over nothing with premultiplied alpha, so the compositor shows the windows below through its transparent parts; an opaque window keeps XRGB8888, composed over black, which the compositor never has to blend.
- A layer with a parent, such as a `SurfaceView`'s, opens no window. Its frames are kept and composed in software into its window, the part SurfaceFlinger plays (`crates/system/src/scene.rs` and `compose.rs`). `SurfaceControl.Transaction` is ours: its setters only record changes, and `apply` makes them all at once, under the lock composition reads the tree with, so a window never shows half a transaction; `merge` moves another transaction's changes after its own, and a transaction merged into a `BLASTBufferQueue` waits for that queue's next frame, as SurfaceView's position waits for its window's. Order is SurfaceFlinger's: children with a negative z below their parent's frame, the others above, by z, and a layer placed relative to another, as SurfaceView's is to its window, draws among that layer's children with its own parent's geometry. Position and matrix compose down the tree, crops and frame sizes clip a layer and its children, alpha multiplies, buffer transforms flip and turn the frame, and corner radius rounds a layer whose transform keeps the axes (any other turn is clipped to its bounding box). A layer reparented to nothing leaves its window.
- A child layer whose frames are GPU dmabufs leaves its window's composition for a plane: a desynchronized `wl_subsurface` of the window's surface, without input, so every event still reaches the window. The composer reports where it would have drawn the layer (`scene::External`), and the plane is put there, below the window's surface when the layer draws below the window's frame, as a `SurfaceView` does, else above. A window with a plane below it is composed over nothing in ARGB8888, so the hole `SurfaceView` clears in the window's frame shows the plane, as SurfaceFlinger shows it. Only a layer moved by whole pixels, unscaled, unturned, opaque to its parents' alpha, unrounded and unclipped goes on a plane; any other goes back to composition with its frames read back, and so does a layer whose app posts software frames again.
- Only what changed is redrawn. `Surface.lockCanvas` keeps the requested dirty rectangle and clips the Canvas to it, since the Bitmap keeps the last frame, as Android's back buffer does; posting copies only those pixels, and composition redraws only the damage: what each layer posted, where it is now, and where a moved, changed or removed layer was. The compositor is told the same damage.
- `DisplayEventReceiver` paces `Choreographer` with a timer fd on the receiver's Looper, registered through the framework's `MessageQueue.addOnFileDescriptorEventListener`, and the timer follows the compositor: every frame a window presents asks for a Wayland frame callback, and while one is pending, a scheduled vsync, including one an animation asked for before the frame was drawn, waits for it and fires when it comes, then calls `dispatchVsync`, as Android's receiver does when SurfaceFlinger's event arrives. So an app draws at the pace the compositor shows its frames, 30 Hz when the compositor shows 30, but never faster than the 60 Hz the display reports, and never two vsyncs closer than one period. With no callback pending, such as before any window exists, vsyncs fire on a 60 Hz clock on `CLOCK_MONOTONIC`; a vsync waiting for a callback fires anyway after three periods, since compositors send none to hidden windows, so a hidden app keeps running at about 15 Hz instead of stalling. `IWindowManager` reports an animator duration scale of 1, since its default of 0 reads as animations turned off and ends every `ValueAnimator` after one frame.

Input takes InputDispatcher's place, in the same process:

- `addToDisplay` opens the window's `InputChannel` pair, a `SOCK_SEQPACKET` socket pair as on Android, keeps the server end and hands `ViewRootImpl` the client end; `relayout` attaches the server end to the window's layer. The host library has no `InputChannel` or `InputEventReceiver` natives, so both are ours: the receiver watches its end on its Looper, as the vsync timer is watched, and hands framework `KeyEvent`s and `MotionEvent`s to `dispatchInputEvent`. The records crossing the socket are ours too, since both ends are this library.
- The Looper of the thread that first draws a window watches its Wayland connection, so seat events and the compositor's pings are read while nothing draws, and also after each frame's round trip. The pointer is a mouse (hover, buttons, wheel, side buttons as `BACK` and `FORWARD`), touch points are fingers of one touchscreen, and keys map from evdev codes to key codes by position, as AOSP's `Generic.kl`. An activated toplevel is the focused window, reported through `onFocusEvent`.
- Characters come from the compositor's keymap, read with libxkbcommon, which is opened at the first key. The host library's `obtainEmptyMap` holds no native map, so its overlay cannot apply, and every `KeyCharacterMap` native is ours, over that keymap, as a full keyboard. `IInputManager` lists the seat's keyboard, mouse and touchscreen.
- As InputDispatcher does, a key the app does not handle that has a fallback, `ESCAPE`, comes back as its fallback, `BACK`, with `FLAG_FALLBACK`. Without predictive back, `BACK` reaches `Activity.onBackPressed`.
- RustDesk's Flutter text field takes typed key events with no input method service; that service, and `audio` for a click's sound, are answered by defaults. Which path inside Flutter carries the text was not traced. `runtime/framework/input_smoke.sh` and, in the sandbox, `rustdesk_input_smoke.sh` check this through a scripted compositor, `input_compositor.py`, which injects seat events and reads frames back. `Process.readProcLines` is ours too, because the framework reads `/proc/self/status` after each garbage collection and stops the process when that fails.

Real apps ask for more. `content`, `clipboard` and parts of other services are answered by defaults. Storage is one emulated shared volume under `ANDROID_DATA/media/0`, the user is unlocked so credential-protected storage opens, the serial number is `Build.UNKNOWN` as for any app without the privileged permission, and the app has an install source. `Activity.reportFullyDrawn` is printed, because Flutter calls it after its first frame. RustDesk's x86_64 build, a Flutter app, reaches its first frame this way about 380 ms after the framework starts, checked by `runtime/framework/rustdesk_smoke.sh` in the sandbox.

The app has an Android identity of its own, apart from its Linux one. Android runs each app under an application uid, 10000 to 19999, and its framework reads uid 1000 as the system: WebView refuses to start in it ("not allowed in privileged processes") and TrafficStats cannot initialize. The process keeps the user's Linux uid, which owns the app's files and is the one the control socket checks, and the framework sees `10000 + FNV-1a(package) % 10000`, stable for a package on every install and host: `Binder.getCallingUid` returns it, since every call comes from the app itself, `Process.myUid` is rewritten at build time to call it instead of `Os.getuid` (`rewrite_classes.py`), and `ApplicationInfo.uid` holds it. Native code calling `getuid` still sees the Linux uid. The device describes itself as uxdroid, an x86_64 user build signed with release keys (`assets.py build-prop`), not as the Robolectric build the framework comes from: apps read a fingerprint of `robolectric` as a unit test, and AnkiDroid then skips loading its native library. The framework jar also carries `javax.microedition.khronos`, the EGL10 and GL10 interfaces `GLSurfaceView` hands its renderer.

#### WebView, a future provider

AnkiDroid's `Application` calls `CookieManager.getInstance()` and `WebView.setWebContentsDebuggingEnabled`; both reach `WebViewFactory.getProvider`, which finds no provider (the device has no `android.software.webview` feature, as `hasSystemFeature` answers), AnkiDroid records that WebView failed, and its `DeckPicker` opens a modal "Fatal error: AnkiDroid relies on the System WebView" over the deck list. Its reviewer, card previews, statistics and deck options are web pages too, so AnkiDroid is not usable without a provider, and pretending to have one that renders nothing would only move the failure. A provider is `android.webkit.WebViewFactoryProvider` and its delegates (`WebView`, `WebSettings`, `CookieManager`, `WebViewClient` callbacks, `evaluateJavascript`, `addJavascriptInterface`, `shouldInterceptRequest`), drawing into the View's canvas or a `SurfaceView`. Candidates, none tried yet:

### The package manager knows every installed app

Every app installed over the same data directory is visible to every app's `IPackageManager` (`dev.uxdroid.system.Packages`), so an app store can list, look up and resolve the others, and any app finds its own default activity: the running app, and each other `ANDROID_DATA/app/<package>/base.apk`, read from its install record, which holds the application's meta-data and every activity, receiver, service and provider with its meta-data and intent filters (format 3; an older record is refused and the APK parsed). A record that is missing or stale for the runtime or the APK falls back to the framework's parse of the APK, as a start does. Another app's record is read as hostile: one larger than 4 MiB (microG's, the largest seen, is 157 KB) or nested deeper than 64 values is refused before anything is allocated, it names only framework classes, which are looked up without being initialized, and the APK is parsed instead. An app is read again only when its identity changes, so one installed while another runs is found on the next query.

| Call | Answer |
|------|--------|
| `getApplicationInfo`, `getPackageInfo`, `getInstalledPackages`, `getInstalledApplications`, `getAllPackages`, `getPackageUid`, `getPackagesForUid`, `getNameForUid`, `getTargetSdkVersion`, `isPackageAvailable` | Any installed app; meta-data only with `GET_META_DATA`, as Sentry reads `io.sentry.auto-init`, and components of `PackageInfo` from the record, enabled ones unless `MATCH_DISABLED_COMPONENTS` |
| `getActivityInfo`, `getReceiverInfo`, `getServiceInfo`, `getProviderInfo` | Any declared component of any app, null when it is disabled unless `MATCH_DISABLED_COMPONENTS` |
| `queryIntentActivities`, `queryIntentReceivers`, `queryIntentServices`, `queryIntentContentProviders`, `resolveIntent`, `resolveService` | The component an intent or its selector names, else every enabled component one of whose filters matches, with `MATCH_DEFAULT_ONLY` only filters with the default category; another app's component only when it is exported, as Android 12 and later. Ordered by priority, default category and match; where Android would let the user choose between equally good activities through `ResolverActivity`, `resolveIntent` takes the first |
| `getComponentEnabledSetting`, `setComponentEnabledSetting(s)` | Kept per package in `ANDROID_DATA/system/components/<package>`, one `<state> <class>` line each, replaced by a rename, so they last across starts and updates and every app reads them; an app changes only its own components (another's is a `SecurityException`, as without the system's permission), and is never restarted for it. Providers at bind and queries honor them |
| `canRequestPackageInstalls` | For the caller only: true when its manifest requests `REQUEST_INSTALL_PACKAGES`, since a requested permission counts as granted |

Application uids come from a hash of the package name, so two packages can share one, such as `com.example.compat` and `com.example.a11245`: `getPackagesForUid` lists every package that has it, the caller first, and `getNameForUid` names the caller for its own uid. `setComponentEnabledSettings` checks every entry before it writes any. Package visibility is not applied: Android 11 and later show an app only the packages its `<queries>` name, while here every installed app sees all the others. Starting another app's activity is refused as above; binding another app's service and reaching another app's provider still need processes that talk to each other, which do not exist yet, so a lookup finds them and a connection does not reach them.

Not yet: key repeat, a soft keyboard and the input method service, pointer capture and cursors, drag and drop, more than one seat, sub-windows placed relative to a parent that is not at the display's origin, dim layers behind dialogs, color layers, `setGeometry` and `setDestinationFrame`, a window of its own for a second activity (it is a subsurface of the first one's toplevel, and goes with it), hardware rendering of views (hwui stays in software), screenshots of planes for agents (a `screenshot` shows the window's own frame, with the hole where a plane shows), and explicit synchronization with the compositor.

The spike measured 28 MiB of private dirty memory per process. Most of the rest was clean framework pages, shared between processes.

### Installs verify signatures and choose splits as Android's installer does

`uxdroid install` treats every APK as hostile and verifies it before reading anything else, with the order and rules of Android's `ApkSignatureVerifier`: only the strongest scheme present is checked (v3.1 or v3 for SDK 36, then v2, then the JAR signature), a JAR signature that says v2 or v3 existed, or a v2 signer that says v3 existed, is refused as stripped, and an app targeting SDK 30 or later needs v2 or later. The parsers are our own (`crates/apk/src/signing.rs`, `der.rs`), on RustCrypto's audited primitives (`sha1`, `sha2`, `rsa`, `p256`, `p384`) rather than OpenSSL, so the CLI keeps no C dependency; every length in the signing block, the DER and the JAR manifests is checked against what holds it. The update rule is Android's too: the installed app's signer certificates, recorded at install, must equal the update's; v3 key rotation is not followed yet.

Split APKs follow Android's layout, so the framework's own `PackageParser`, which parses a directory of `base.apk` and `split_*.apk` as one package, can read them: the chosen splits go beside `base.apk` in `ANDROID_DATA/app/<package>`, listed in `splits`. Choosing configuration splits needs no device: the ABI, the framework's 160 dpi and the user's locale decide, as Play's device targeting does, and bundletool's `toc.pb` picks the SDK variant. Feature splits with code are compiled after the base, in the base's class loader context, named relative to the staging directory with `--classpath-dir`, as installd does, since their installed paths do not exist yet and ART matches context entries by name. At start the launcher sets `ApplicationInfo.splitNames`, `splitSourceDirs` and `splitPublicSourceDirs` from the `splits` list, and the framework's own `LoadedApk` does the rest: split code after the base's in one `PathClassLoader`, split resources in the app's `AssetManager`. The install record's identity also names each split's size and modification time, so a changed split makes the record stale, while an APK without splits keeps the identity, and the record format, it had. Isolated splits (`android:isolatedSplits`), which get a class loader per split, are not tested.

### One process per app, driven through a control socket

Android keeps one process per app, and two processes over one data directory can corrupt its databases and preferences, so the launcher allows one. It holds an exclusive `flock` on `ANDROID_DATA/app/.<package>.running` for the life of the process; the kernel drops it when the process ends, however it ends, so a crash leaves no stale lock, and the file closes on exec, so programs the app runs do not inherit it. A launch that finds the lock held hands its intent to the running process through its control socket, prints `uxdroid: <package> is already running as process <pid> over <data>, so this launch went to it: <outcome> <activity>`, and exits 0; the running instance may still be starting, so the socket is tried for up to 30 s. A lock that cannot be taken at all, as on a read-only directory, is reported and the app runs anyway.

The running app's activities form one task, `dev.uxdroid.system.ActivityStack`, which decides what an intent does as `ActivityTaskManager` does, and tells the framework through its own client transactions:

| Intent | Result |
|--------|--------|
| The launcher's (`MAIN`, `LAUNCHER`, no data) while an activity runs | `brought_forward`: nothing changes |
| For the activity on top, which is `singleTop`, `singleTask` or `singleInstance`, or with `FLAG_ACTIVITY_SINGLE_TOP` | `new_intent`: `onNewIntent`, then resumed |
| For an activity lower down, with `FLAG_ACTIVITY_CLEAR_TOP` or a `singleTask` launch mode | The activities above it finish; `new_intent` if it is single-top as above, else it is made again, `launched` |
| Anything else | `launched`: a new activity on top |

An intent names an activity by class, or `.Name` relative to the package, or is resolved by the manifest's intent filters with the default category, as `startActivity` resolves an implicit one; a launcher's intent goes to the launcher activity, the first `MAIN` and `LAUNCHER` one the manifest leaves enabled, as a home screen shows only those (F-Droid declares a disabled calculator disguise before its real screen). Each activity has its own window, as in desktop windowing, so an activity covered by a newer one is paused, not stopped, and its window stays. `Activity.finish` destroys the activity and resumes the one below; when the last one finishes, the process exits, as a desktop app does when its last window closes. An app's own `startActivity` goes through the same stack, as Markor's and AnkiDroid's first activities start their real screens: an intent for one of its activities starts as above, `FLAG_ACTIVITY_NEW_TASK` with `FLAG_ACTIVITY_CLEAR_TASK` first finishes the task, and an intent none of its activities takes fails with `ActivityNotFoundException`. So does one that another installed app's activity takes, below, since that app runs in its own process and an app cannot start one yet: the exception names the activity and says so, and apps already handle it as no app taking the intent. `startActivities`, as `TaskStackBuilder` and Navigation's deep links start a back stack, starts each intent in turn, so each activity is made at once, where Android makes the lower ones only when the user goes back. A result goes back as Android sends it: `startActivityForResult` records the asking activity and request code on the one it launches, and when that one finishes, what `setResult` left reaches the asker as an `ActivityResultItem`, so `onActivityResult` runs before it resumes; a start that launches nothing new, by launch mode or flag, answers `RESULT_CANCELED` at once. `PendingIntent`s are made in process as the activity manager makes them (`IntentSenders`): the same request, by type, request code, the flags that are not only about getting it, and `Intent.filterEquals`, gives the same one, the flags that create, cancel, update or send once do what they do on Android, and sending one for an activity starts it in the task, and one for a broadcast delivers it as `sendBroadcast` does, below; one for a service is accepted and not delivered, which is said once.

Broadcasts stay in the app, since other apps run in processes of their own (`Broadcasts`). A receiver the app registers gets every broadcast its filter matches, and one its manifest declares only an explicit broadcast, naming the app's package or the receiver, as Android has kept implicit broadcasts from manifest receivers since 8.0. A normal broadcast reaches all its receivers at once, each run on the main thread by the framework's own dispatchers (`IIntentReceiver.performReceive` for a registered one, `scheduleReceiverList` for one of the manifest); an ordered one goes to one receiver at a time by priority, each `finishReceiver` passing its result to the next and the last to the sender's result receiver, and ordered broadcasts queue one behind another. A sticky broadcast is kept, and a receiver registered later gets the last one it matches. Permissions of senders and receivers are not checked, since both are the app.

The control socket is `<dir>/<package>.sock`, where `<dir>` is `$XDG_RUNTIME_DIR/uxdroid`, or `/tmp/uxdroid-<uid>` without a runtime directory. The directory is made with mode 0700, and an existing one that is not the user's, or that other users can enter, is refused rather than repaired; the socket has mode 0600, and each connection's peer uid, from `SO_PEERCRED`, must be the app's own, or it gets `not_allowed` and nothing else. The socket is served once the main thread is first idle after the launch: served at once, it delayed the sample app's first frame by about 5 ms, though binding it takes 0.3 ms, for a reason not found. A thread of `crates/system` accepts connections, one thread per connection reads its requests in order, and every request is checked before the app sees it. A checked command is queued for the main Looper, which watches an eventfd through `MessageQueue.addOnFileDescriptorEventListener` and runs it between the app's own messages, so the framework is only touched on the thread it expects; a main thread that does not answer within 10 s gets the command `busy`. At most 16 connections are served at once, and one idle for 30 s is closed. A socket file whose owner died is replaced: ownership is a second lock, `<dir>/<package>.lock`, held as long as the socket is served. The socket is per package, profile and user. A profile is one instance of a package over its own data directory, as a second user of a phone has: `UXDROID_PROFILE` names it, its socket and lock are `<package>@<profile>.sock` and `.lock`, and the default profile keeps the package's own names, so a launch without a profile behaves as before. An instance over another data directory under the same profile runs without a socket and says so. A clean exit, through `stop` or the last activity finishing, removes it. A socket that cannot be served costs only the control, never the app.

A service manager can bind the socket instead and start the app on the first connection, as a systemd socket unit does. The launcher then serves the descriptor it was passed and binds nothing. It reads `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` as `sd_listen_fds` does: they count only when `LISTEN_PID` is this process, so a program the app runs that inherits them ignores them; the descriptor is the only one passed, or the one named `control`; anything else set wrong is reported and the socket is not served. The descriptor must be a listening Unix stream socket bound to the instance's own path, else it is refused; it is made to close on exec, its file is set to mode 0600 like a bound one, and the ownership lock is taken as for a bound one, so the peer check, the instance lock and `uxdroid app` work unchanged. Its file is the manager's, so a clean exit leaves it, and the next connection starts the app again. A launch that finds the socket file listened on by no instance, which is what a socket unit looks like between starts, leaves it alone and runs without a socket: the check reads `/proc/net/unix`, because connecting would start the app. A service start that finds the app already running over the same data directory outside the service cannot hand its launch over, since the socket is its own, so it says so and exits with status 75, which the units do not restart on.

#### Apps as systemd user services

`uxdroid service enable` writes a socket unit and a service unit per package and profile, `uxdroid-<package>@<profile>.socket` and `.service`. The socket unit listens on the instance's control socket, so the first connection starts the app through `uxdroid service run`, which becomes the launcher in the same process and so keeps the process id `LISTEN_PID` names. Per-app units were chosen over one `uxdroid@.service` template because the settings that differ per app (data directory, address families from the manifest, memory and CPU limits, start at login) are most of the unit, and a template would need a drop-in per app to hold them. The service restarts on failure, at most 5 times a minute, logs to the journal, and runs in its cgroup's limits; its hardening keeps the file system read-only but for the data directory and the control directory, and allows only Unix and netlink sockets, plus IPv4 and IPv6 for an app whose manifest names `INTERNET`. That check searches the manifest's string pool for the name, so it errs toward allowing the network, never against an app that asks for it. Every path in a unit is resolved when it is written, escaped for systemd's specifiers, and refused if a unit word cannot hold it; a unit file not marked as written by `enable` is never replaced or removed. `systemctl` runs only with `--now`. `uxdroid app` commands other than `start` connect only to an instance that holds its ownership lock, so asking about an app never starts it.

#### Protocol, version 1

One JSON object per line each way, UTF-8, each request answered in order on its connection. A request is at most 64 KiB; a longer one gets `too_long` and the connection is closed. Answers are read up to 16 MiB, for what later commands report.

```text
→ {"v":1,"id":7,"cmd":"start","intent":{"activity":".Detail","action":"android.intent.action.VIEW","data":"example://x","extras":{"k":"v"},"flags":0}}
← {"v":1,"id":7,"ok":true,"result":{"outcome":"launched","pid":4242,"activity":"com.example/.Detail"}}
← {"v":1,"id":8,"ok":false,"error":{"code":"no_such_activity","message":"com.example declares no activity com.example.Nope"}}
```

`v` must be 1, else `unsupported_version`. `id` is optional, a non-negative integer or a string of at most 64 bytes, and is echoed, also in refusals. Unknown fields are refused, so a field a later version adds is never silently ignored.

| `cmd` | Takes | Result |
|-------|-------|--------|
| `hello` | | `versions`, `commands`, `package`, `pid`, answered by the server thread without the main Looper |
| `status` | | `package`, `pid`, `data`, `activities`: `component` and `state` (`resumed` or `paused`), bottom to top |
| `start` | `intent`, optional: the launcher's intent without one | `outcome` (`launched`, `new_intent`, `brought_forward`), `pid`, `activity` |
| `intent` | `intent` naming an activity, an action or data | As `start` |
| `stop` | | `pid` and the number of activities `finished`; the process exits after answering |
| `ui` | `max_nodes` (1 to 5000, 1000), `max_depth` (1 to 128, 64) | `snapshot`, `nodes`, `truncated`, `accessibility`, `windows`: `index`, `title`, `type`, `bounds`, `focused`, `root` node, below |
| `screenshot` | `window` (0 to 63), `max_size` (16 to 4096, 2048) | `width`, `height`, `scale`, `windows`, `png` (base64) |
| `tap` | `node` and optional `snapshot`, or `x` and `y` (0 to 16383) | `x`, `y`, and `node` |
| `type` | `text` (1 to 4096 bytes, no control characters but newline and tab), optional place as `tap` | `typed`, `keys`, `committed` |
| `scroll` | a place as `tap`, `dx`, `dy` (-50 to 50 wheel steps, not both 0) | `x`, `y` |
| `back` | | `key` |
| `key` | `key`, a `KeyEvent.KEYCODE_` name of at most 32 characters | `key` |
| `wait` | `text` (at most 1024 bytes) or `idle: true`, `timeout_ms` (1 to 60000, 10000) | the `node` found, `snapshot`, `waited_ms`; or `idle`, `waited_ms` |

An `intent` holds `activity` (a class name), `action` (at most 255 bytes), `data` (a URI of at most 4096 bytes), `extras` (at most 64 strings, keys of at most 255 bytes, values of at most 4096) and `flags` (`Intent.setFlags`, 0 to 2^32-1); none may hold control characters but extra values. Refusal codes: `bad_request`, `unsupported_version`, `unknown_command`, `too_long`, `not_allowed`, `busy`, `no_such_activity`, `failed`, and for agents `no_such_node`, `stale_snapshot`, `no_window`, `timeout`. A field belongs to its command: any other is refused, as an unknown one is.

Nothing a client sends can make the app run code its APK does not hold: an intent can only start an activity the manifest declares, of the app's own package, and extras are only strings, so no class is named, loaded or deserialized from a request. Agent commands only read views and send seat input: text is typed key by key, never evaluated.

#### Agent control

An agent reads the screen and acts on it through the same socket, and through `uxdroid mcp`. The control server's handler is an agent (`crates/system/src/control/agent.rs`) in front of the main Looper's queue: `ui` and the text an input method would commit go to the main thread; everything else is answered on the connection's thread, through the display's seat and frames.

- `ui` runs on the main thread (`dev.uxdroid.system.Agent`) over every root view `WindowManagerGlobal` holds, bottom first. Each view describes itself through `createAccessibilityNodeInfo`, its own `onInitializeAccessibilityNodeInfo`, which gives class, text, content description, hint, bounds on the screen and the flags Android's accessibility services see. A view with an `AccessibilityNodeProvider` is described by the provider's virtual nodes instead, followed through `getChildId`: that is how Flutter's `FlutterView` reports its semantics tree; Compose's `AndroidComposeView` uses a provider too, which no test here covers. Children of an ordinary view are its own children, all of them, not only those important for accessibility. A view whose node cannot be made falls back to its fields. Nodes are numbered depth first per snapshot; the agent keeps the last snapshot's bounds, so `tap`, `type` and `scroll` name a node and act at its center. Output is bounded in nodes, depth and text, and the answer in bytes (8 MiB).
- Flutter answers through its provider only while accessibility is on, and builds its semantics only then. So the first `ui` registers an `IAccessibilityManager` among the in-process services and connects the app's `AccessibilityManager` to it, which hands over its client; the service tells the clients `STATE_FLAG_ACCESSIBILITY_ENABLED`, touch exploration off, since that would turn hover events into accessibility focus. The flag is per process and lasts while a connection that asked for `ui` or `wait --text` is open; when the last one closes, the service tells the clients it is off. Before an agent asks, no service is registered and the app runs exactly as before. The first snapshot after turning it on is taken when the node count has not changed for two 100 ms polls, at least 300 ms and at most 3 s after.
- `tap`, `type`, `scroll`, `back` and `key` become `wayland::Injected` seat input, placed among the compositor's own events and translated by the same `Translator`, then routed by `windows::Stack` to the window under the point or the focused one: a tap is a touch point down and up 40 ms apart, a scroll is wheel steps at a point that hover there, a key is an evdev code. Typing looks each character up in the compositor's keymap (`KeyCharacterMap`'s own data) and presses its key, with shift around it when its level needs it; only characters no key types are committed through the focused view's `InputConnection`, as an input method would. So the app cannot tell an agent's input from a user's, and Flutter's text field, which takes key events, gets it the way it gets the seat's typed text.
- `screenshot` copies each window's last presented frame, the shared-memory buffer the compositor shows, under that window's own lock, one at a time, and composes them bottom first at their surface positions over black, as the compositor does with subsurfaces; it is pixel for pixel the compositor's frame in `agent_smoke.sh`. One window can be asked for alone. A display larger than `max_size` is sampled down by a whole factor. The image is PNG (`control/png.rs`: 8-bit RGB, one zlib stream through the `flate2` the APK reader already builds), base64 in the answer, at most 12 MiB.
- `wait` polls on the connection's thread, so agents do not sleep: for text, a snapshot every 100 ms until a visible node's text, description or hint holds it; for idle, the count of presented frames, until it has not changed for 500 ms.

`uxdroid mcp` was chosen over `uxdroid app <package> mcp`: an MCP client is configured once, for every app, and an agent can list, start and move between apps. It speaks JSON-RPC 2.0, one message a line on stdio, at most 1 MiB in: `initialize` for MCP versions up to 2025-11-25, and `server/discover` with the version in each request's `_meta` for 2026-07-28, refusing an unknown one with `-32022`. Its tools map one to one onto the commands, each with `package` and `profile` besides the command's own fields, which are checked by the protocol's own parser; bad arguments and refusals are tool errors with `isError` that the agent can read, unknown tools and methods JSON-RPC errors. It keeps one connection per app, so accessibility stays on between calls, and reconnects once when the app closed an idle one. `screenshot` returns MCP image content.

Measured in `agent_smoke.sh` on the input sample, 50 calls on one connection: `ui` 0.66 ms median (11 nodes, 1.8 KB), `screenshot` 2.2 ms (400x700, 19 KB), `tap` 40 ms (its finger stays down 40 ms), and the first `ui` on a connection, which turns accessibility on, 303 ms. RustDesk reports 36 nodes on its home screen through Flutter's bridge. Not yet: a memfd instead of base64 for screenshots, `startActivity` of the app's own, gestures other than taps and wheel steps (drag, long press, pinch), accessibility actions (`performAction`), and a node's id that survives snapshots.

### Audio goes to the host's sound server over the PulseAudio protocol

`AudioTrack`, `AudioRecord` and the `AudioSystem` values they read are natives in `crates/system`, so a Java app's sound reaches the server with no `audioserver` and no Binder in between; `IAudioService` gives players ids, full volume and audio focus. Recording, through any API, needs the manifest's `RECORD_AUDIO`: the launcher records the requested permissions in `dev.uxdroid.system.Permissions`, and a desktop has no dialog, so a requested permission counts as granted.

Every Android audio API an app uses becomes one stream of `crates/audio`: interleaved `f32` frames at the app's own rate and channel count, converted from the app's sample format at the API's edge. Each stream has one thread that moves a 10 ms period, as Android's mixer does, between the stream and the device, whose clock paces it. A push stream, such as an `AudioTrack` in streaming mode, buffers what the app writes and plays silence when the buffer runs dry, counting each gap as one underrun. A callback stream, such as AAudio's data callback or an OpenSL ES buffer queue, asks the app for each period on that thread. `AudioTrack.setPlaybackRate` resamples linearly to the stream's rate. Nothing is mixed in the process: each stream is its own client of the server, which mixes and resamples to the hardware.

`UXDROID_AUDIO` chooses the backend:

| Value | Backend |
|-------|---------|
| unset | The PulseAudio protocol, else ALSA's `default` device, else silence with a warning; the first server or device that opens is kept for the process, while silence is tried again at the next stream |
| `pulse`, `pulse:<server>` | The PulseAudio protocol only |
| `alsa`, `alsa:<device>` | ALSA only |
| `null` | Silence, at the device clock |
| `file:<dir>` | Each output stream writes `output-<n>-<rate>hz-<channels>ch.f32` into the directory, and input streams read `input.f32` from it, then silence; raw little-endian `f32`, at the device clock. Tests read back every sample |

The PulseAudio protocol was chosen over PipeWire's own because it reaches both servers a Linux desktop runs: PipeWire serves it through `pipewire-pulse`, and older systems run PulseAudio itself. Its client library, `libpulse-simple`, is five functions over a blocking stream, against PipeWire's stream API, which needs the format built as SPA pods from inline header code. The latency an app gets is set explicitly: two periods (20 ms) queued on the server, plus the server's own quantum. PipeWire's native API would save the hop through `pipewire-pulse` and could run the callback on PipeWire's real-time thread; that was not measured, because the test environment has no PipeWire server, and is the first thing to try if the measured latency is not good enough. ALSA is the fallback for hosts without a server: two periods of latency, with its own resampler when the device lacks the rate.

The host's sound libraries are opened with `dlopen` when the first stream opens, never linked, so uxdroid adds no build dependency and starts on hosts without them.

Measured on a private PulseAudio server (`benches/framework/README.md`): callbacks every 10.0 ms, 20.4 ms of latency on the server at 48 kHz, and an AAudio stream's first callback within 15 us of `requestStart`. Not yet: marker and period events of `AudioTrack` and `AudioRecord`, `AudioTrack` loop points, AAudio's error callback, shrinking a buffer below its capacity, volume and focus changes from the host, and input and output device selection.

### Guest architecture stays inside the native bridge

The platform is built once, for the host. Only an app's own `.so` files have a guest ABI, and only the bridge knows which one. These rules let `arm64-v8a`, and later `armeabi-v7a`, arrive without changes elsewhere:

1. ART, the framework, the services and our natives have a single host build. Nothing outside `crates/bridge` and `crates/nativebridge` depends on the app's ABI.
2. Every function we expose to app native code, such as `libandroid`, `liblog`, EGL or OpenSL ES, is declared in a machine-readable signature table next to its implementation, as described above. Direct loading binds the table's addresses. A translator generates guest-to-host trampolines from the same table.
3. App native code reaches the platform only through JNI and those functions. ART passes each JNI method's shorty to `get_trampoline`, which is where a translator wraps guest code.
4. Calling-convention shortcuts stay on the host side. The default bodies above are called only by host ART, never by guest code.
5. Install time picks the ABI: the host's when the APK has it, otherwise a guest ABI the translator supports. The choice is recorded with the install.

`armeabi-v7a` also needs pointer and struct conversion between 32-bit guest code and the 64-bit host at every crossing. That is the translator's job and is not designed yet.

## Known limit: Google Play

Installing apps through the Play Store requires Google Play Services, which is proprietary and designed for certified devices. Apps that use the [Play Integrity API](https://developer.android.com/google/play/integrity/overview) can check for a certified device, and uxdroid will not be one. Expect those apps to refuse to run, whatever the quality of this layer.
